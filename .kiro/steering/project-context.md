# Project context — Mitsui Well Data Assistant POC

A read-only natural-language assistant over Mitsui's oil and gas well data on AWS (Control
Tower landing zone, VPN + PrivateLink, DMS from SQL Server to S3 Tables, Glue/Athena,
Lake Formation masking, Bedrock Claude via AgentCore, MCP tools, Teams bot). SOW
SOW2026001. This repository is the planning parent; code lives in two submodules.

## context-1: one story, one repository

**Rule.** A story changes only the repository in its `repo:` front-matter field:
`project-mep-AWS-Infrastructure`, `project-mep-AWS-Code`, or `planning` (this parent repo).
Every path you write in a code story is under that submodule; planning files
(`user-stories/`, `task-list/`, `adr/`, `knowledge/`, `harness/`, `.kiro/`) never go into a
submodule, and code never goes into the parent. The harness context block at the top of
each prompt names the target repository.

**Why.** ADR `user-stories/docs/0002-repo-structure-and-roles.md`: each submodule is handed
over to Mitsui on its own.

**Check (driver).** `harness/run_story.py` runs git and `scripts/validate.sh` inside the
target repository only; files outside it never reach the story's commit.

## context-2: read the decisions before you plan

**Rule.** Before planning, read the story file, then the sources below that it touches.
Cite what you relied on in the plan (file path + section). When a source and the story
disagree, stop and raise it as an open question; do not pick one silently.

| Source | What it decides |
|---|---|
| `user-stories/WDA-POC-Feature-List.md` | Features F1–F14, dependency register, end-to-end acceptance scenarios, known conflicts, proposed decisions, open questions |
| `user-stories/config/parameters.md` | Every Mitsui value by parameter name, placeholder and status. Code reads values by these names |
| `user-stories/dependencies/README.md` | DEP-01..DEP-29: type (A value, B secret, C approval, D Mitsui action, E design decision), owner, due, status |
| `user-stories/docs/0001-*.md`, `0002-*.md` | How stories are tracked; repository structure and roles |
| `adr/WDA-POC-Data-Workflow.md` | Data flow from SQL Server to the assistant; load and access design |
| `adr/WDA-POC-AWS-Run-Cost-Estimate.md` | Cost envelope; sizing must stay inside it |
| `adr/WDA-POC-Architecture.drawio` | Architecture diagram (XML; read labels if needed) |
| `knowledge/Mitsui-WDA-POC-Client-Dependencies-and-Sharing-Strategy.md` | What Mitsui supplies, how it is shared, and what the harness may never see |
| `harness/context/knowledge/mitsui-capnexus-sow2026001-*.md` | The SOW (converted from PDF): deliverables D1..., scope, out of scope |
| `harness/context/knowledge/mitsui-well-data-assistant-poc-kickoff-agenda.md` | Kickoff agenda (converted from .docx) |
| `task-list/week-N/*.md`, `harness/context/task-list/wda-poc-task-list.md` | Day-by-day plan, owners, freeze dates |

`harness/context/` is generated by `.bootstrap/prepare_inputs.py`; regenerate, never edit.

**Why.** The stories are short on purpose; the decisions behind them live in these files.

**Check (review).** The reviewer rejects a plan that contradicts a cited source or an
`accepted` ADR without raising it.

## context-3: dependencies, secrets and human gates

**Rule.** Build against the placeholder in `config/parameters.md` for every type A value.
Type B values are referenced by Secrets Manager secret name only; never ask for, write or
log a secret. Stop at every `gate:` acceptance criterion and every `human_gates` entry:
prepare the evidence and leave approver, date and decision blank for the person.
Design decisions (type E: DEP-06, DEP-27 and similar) belong to the solution architect,
Soma; other owners are named in `dependencies/README.md`.

**Why.** Mitsui's values, approvals and environment are outside the harness's control.

**Check (grep + review).** `scripts/hooks/scan-secrets.py` blocks secret-looking content;
the reviewer rejects a filled-in approval the agent could not have witnessed.

## context-4: freezes

**Rule.** No load-pipeline changes from 2026-12-14 (unattended-load window, Dec 14–25) and
no code changes from 2026-12-18 except fixes for failed tests, which need a human override.

**Why.** Task list, week 5.

**Check (validator).** The `freeze` stage of `scripts/validate.sh`.

## context-5: planning-repo stories

**Rule.** For `repo: planning` stories the CDK/npm rules do not apply. Checker scripts are
Bash under `user-stories/scripts/` named `check-*.sh` (exit non-zero on failure); their
tests are Bash scripts under `user-stories/scripts/tests/` with valid and invalid fixtures.
`verify:` paths written as `scripts/...` in a story mean `user-stories/scripts/...`.

**Why.** `user-stories/README.md` layout; the validator's planning mode runs exactly these.

**Check (validator).** Planning mode runs every `check-*.sh` and every test script.

## context-6: baseline in Infrastructure, project in Code

**Rule.** `project-mep-AWS-Infrastructure` holds the AWS baseline the project runs on:
landing zone and accounts, Region-deny, IAM Identity Center and the trusted token issuer,
the workload VPC, subnets and security groups, VPN, PrivateLink endpoints, the shared KMS
key, budget, the baseline pipeline and teardown. `project-mep-AWS-Code` holds the project:
all application code **and every AWS resource that exists only for it** (DMS, staging
bucket, source secrets, load jobs, alarms, S3 Tables, catalog, Lake Formation, Athena
workgroup, tools, Gateway, Policy, assistant, Teams bot, audit, project pipeline and
teardown). The test: would the resource stay if the project were replaced? Yes →
Infrastructure; no → Code.

In a Code story:
- Never create, import-and-modify or add rules, routes or subnets to a baseline resource.
  Read baseline values from SSM Parameter Store under `/mep/baseline/` (names in ADR 0002,
  "The baseline contract") through one lookup module; unit tests stub those names.
- Put DMS only in `/mep/baseline/subnets/dms` with `/mep/baseline/sg/dms`, and tools and the
  assistant only in `/mep/baseline/subnets/tools`. Encrypt with `/mep/baseline/kms/key-arn`.
- If the story needs a baseline value that is not in the contract, stop and raise it as an
  open question: the fix is an Infrastructure story that publishes it, not a Code workaround.

In an Infrastructure story:
- Never add project resources. Publish any new value Code needs under `/mep/baseline/` and
  add it to the ADR 0002 contract table in the same change (planning edit noted in the PR).

**Why.** ADR 0002: the baseline is deployed first and torn down last, and network isolation
(only the DMS subnet reaches the VPN) is enforced by the baseline, not by project code.

**Check (review).** The reviewer rejects a Code change that defines an `ec2.Vpc`,
`ec2.Subnet`, route, VPN, VPC endpoint, KMS key or Control Tower/Identity Center resource,
or that hard-codes a baseline ID instead of reading `/mep/baseline/*`; and an
Infrastructure change that defines DMS, Glue, Lake Formation, Lambda tools, AgentCore or
bot resources.
